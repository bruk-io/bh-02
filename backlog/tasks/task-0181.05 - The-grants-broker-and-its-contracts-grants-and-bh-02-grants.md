## Implementation Plan

<!-- SECTION:PLAN:BEGIN -->
The broker is a plain value in `runner_cordis_plugin/broker.py` (no cordis), bound by a component `runner:grants` (row id `grants`, provides `grants`) that depends on `host` alone (pinned by the shell, so the row never reloads). `/grants` is registered by a component `runner:grant_prompt` (row id `grant-prompt`, depends on `grants` and `commands`); TASK-0181.06 adds its prompt (`output.choose`, `serve`) to the same row.

The broker (decision-0012 item 7):
- `need(request) -> release`: a row's standing need, used with `acquire`. Held needs are asked once when a prompt is served (one prompt per distinct grant, however many hold it). A need answered `once` is applied only while some row holds it; the answer is remembered for the session, so a remounted row is not asked again. `always` goes to the store and stays after the need leaves. `no` is remembered for the session and not asked again.
- `async ask(request) -> Answer` (`once`, `always`, `no`, `standing`): `standing` when the grant is already held (store or session); `no` without asking when the session answered `no` to it, or when no prompt is served; else the served prompt, one at a time, with concurrent asks for one grant sharing one prompt. A prompt that returns None (Ctrl-C) records nothing and answers `no`. Whether a grant is already inside the policy (item 5's "standing") is TASK-0181.08's: here, `standing` means already granted.
- `async granted() -> Grants`: the store, read at each call off the event loop (so an `always` or a revoke from another process counts at the next start), then the session's `once` grants of `ask` and of held needs. `BrigJail._granted` becomes a read of this, and `BrigJail._session` goes; `runner:confined` takes `grants` as a dependency (a Protocol of its own: `granted`).
- `on_change(fn) -> release`, `serve(prompt) -> release` (one prompt at a time: a second serve raises with what to do), `list() -> tuple[Entry, ...]` (id, request, answer, `session` or `project`), `revoke(id)` (a session grant leaves the session, an always-grant is removed from the store through `store.write`; an unknown id raises with the ids there are). An id is short and stable across processes: the first 8 hex digits of the SHA-256 of the grant's `str`, so `/grants` and `bh-02 grants` agree.
- A store that is `store.Refused` grants nothing and says so: `granted()` raises nothing; the start's notice carries the words (as a floor refusal does).

`/grants` lists (`list()`, one line each: id, kind, target, answer, scope, who asked and why) and `/grants revoke ID` revokes. `bh-02 grants` and `bh-02 grants revoke ID` do the same outside a session: the CLI boots a composition of the host row and the `grants` row only (by name, importing no plugin: plugin-layering), reads the bound `grants` value through a Protocol of `bh_02`'s own, and prints. A revoke from either is gone at the next start (the store is read at each start).

The sub-agent realm exposes `grants` besides `runner`, `approval`, `host` and `asker`, so a child's rows ask the one broker (decision-0002's list gains it, with why).

CONTRACTS.md gets rows for `grants` (its methods and promises) and `/grants`; the shipped layer (`bh-02.toml`) gets the two rows; the runner README says what the broker holds and why approval depends on neither row.

### Risks
- A dependency that reloads what must not: `approval` must depend on neither row (test: a grant and a requester's remount leave approval's fiber up), and `confined` must not reload when the store changes (the broker is bound once; its value changes, not the binding).
- Two processes writing `grants.toml`: the CLI and a session. `write_beneath` replaces whole; a lost update is possible and accepted here (the next `always` rewrites from a fresh read). Read-modify-write in one function, read fresh each time.
- The CLI booting a composition: keep it to two rows, with no ui and no jail.

### Proof
Unit tests for the broker; a wiring test that a need is asked once, applied while held and gone when the row leaves, and that approval's fiber survives both; a runner test that `granted()` feeds the start; a CLI test that `bh-02 grants` lists and revokes against a temp state directory; `scripts/check` and `scripts/linux-jail-check` (both modes) green.
