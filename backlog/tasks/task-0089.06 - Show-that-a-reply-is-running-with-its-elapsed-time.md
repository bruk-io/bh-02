## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Owner's pick (2026-10-15): while a reply runs nothing on screen moves until output arrives, so a long tool call looks like a hang.
<!-- SECTION:DESCRIPTION:END -->

## Acceptance Criteria
<!-- AC:BEGIN -->
- [x] #1 While a reply runs, the screen shows that it is working and for how long (seconds, then minutes), updated about once a second by a timer, never a loop
- [x] #2 It goes away when the reply ends, is stopped or fails, and comes back for the next
- [ ] #3 Must not break: tui:ui depends on nothing but its config; nothing blocks the event loop; the slash list, the palette, the question and approval screens and Ctrl-C behave as before except where this task says; a Pilot test for each key or view; scripts/check passes

## Implementation Plan

<!-- SECTION:PLAN:BEGIN -->
1. render.py: two pure functions: `elapsed` (7s, 1m 05s, 1h 02m) as private and `working_line(seconds)` public, tested without an app.
2. widgets/working.py: `Working`, a one-line Static between the transcript and the list of commands, hidden until its first tick. `begin()` takes the time from an injected clock and starts a Textual interval timer (`set_interval`, 1 s); each tick redraws "Working · 7s"; `end()` stops the timer and hides it. Never a loop or a sleep: nothing runs between ticks, the tick is a few cells of text.
3. app.py: `BhApp(clock=, working_every=)` seams (the time and the interval), compose the widget, begin on TurnStarted when no reply was streaming (the `_replying` counter 0 -> 1), end when it returns to 0 (TurnEnded fires for finished, stopped and failed alike: the output posts it in a finally).
4. Tests (Pilot, the clock a fake and the interval short, plus one at the real 1 s): shown with the elapsed time after the first tick, advances, minutes; gone on end, on Ctrl-C/Esc stop, on a provider that raises; back for the next with the time from zero; a reply that ends before the first tick never shows it (a command answer goes through the same show); the transcript still follows its end when the row appears and goes; the list, palette, question and Ctrl-C as before (the existing tests); via the real TuiOutput.show.
5. Plant: remove the end() call -> tests fail; make begin() restart each reply... (see notes). Docs: tui README, commands.md if it lists what the screen shows.
Risks: the one-row layout change moving the transcript (guarded by a test on its end staying in view); a reply too short to show it; commands answered through show flashing it (hidden until the first tick).

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
Built: render.working_line (pure; `_elapsed`: 7s, 1m 05s, 1h 02m) and widgets/working.py, `Working`, a one-line Static between the transcript and the list of commands, hidden until its first tick. `begin()` takes the start from an injected clock and starts a Textual timer (`set_interval`, `WORKING_EVERY` = 1 s); each tick redraws "Working · 7s" and shows the line; `end()` stops the timer and hides it. BhApp(clock=, working_every=) are the seams; the app begins it on the first TurnStarted (the `_replying` counter 0 -> 1) and ends it when the counter returns to 0. TurnEnded is what the output posts in a finally, so finished, stopped (Ctrl-C/Esc cancel `show`) and failed (a provider that raises) all end it; the next reply counts from its own start. Nothing loops or sleeps: between ticks nothing runs, and the tick is one text update. Docs: tui README ("Working" paragraph), app.py docstring, commands.md.
Judgments: (1) the first tick is a second in and the line is hidden until then: a command's answer goes through the same output.show (TurnStarted/TurnEnded) and would otherwise flash the row and nudge the transcript for every /help; a reply under a second shows nothing. (2) The line is for replies: a command still running (a ! command, /compact) is shown only when it answers (chat.converse), so it shows no line; filed as TASK-0089.10, not started. (3) The line sits above the list of commands, between it and the transcript; it takes a row from the transcript only while shown (display toggled), and the transcript stays anchored to its end (test).
Clock: a seam for the time (`clock`) and for the interval (`working_every`), with `pilot.pause` in a short poll (`_until`) to let the timers fire; one test runs the real clock and the real 1 s interval and sees nothing at 0.4 s, then "Working · 1s", then "Working · 2s".
Tests (as root, uv run): tests/test_tui_working.py, 24 tests: 10 pure on the words; Pilot: shows the time and advances it by the timer (7s, 1m 05s); sits between transcript and composer in one row; a long interval shows the clock is read only by the tick; keys reach the composer between ticks; goes at the reply's end, back for the next from zero; overlapping replies one line until the last ends; a reply ending before its first tick never draws it (content still empty); through the real TuiOutput.show with a reply waiting on a long tool call: finishes / Esc / Ctrl-C / provider raises each take it down, and the next reply shows it again; the transcript keeps its end in view and follows new output as the row comes and goes; the list of commands opens under it, Esc closes only the list, the palette opens and closes over it, a question is answered, and the line still counts after.
