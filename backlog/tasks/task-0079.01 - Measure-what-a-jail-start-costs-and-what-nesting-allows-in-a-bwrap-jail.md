## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
decision-0001 rests on numbers nobody has: what a jail start costs, whether nested user namespaces work inside a bwrap jail, what a per-process namespace bundle costs, and how the kernel treats signals to a supervisor that is the jail's PID 1. This spike measures them on Linux (bubblewrap 0.9, this container) and writes the answers down; macOS is out of reach here and is named as unmeasured. Its answers gate the supervisor (step 4) and the namespace bundle.

## Implementation Plan

<!-- SECTION:PLAN:BEGIN -->
1. Jail start (AC1): a script compiles strict_linux() for an allowlist Spec with one LISTEN channel and launches it with SubprocessLauncher (tethered, like bh-02), ready = Handle.wait_ready() returned (a host connect to the socket the jail's python3 bound); split compile vs launch-to-ready; kill each run. 1 discarded + 20 timed runs, as root and as tester. Beside it, the bare bwrap argv brig composes with a workload that writes one byte to an inherited pipe, to separate bwrap from brig's wrappers.
2. Namespace bundle (AC1): inside one running jail started with brig's composed argv, a python3 program forks a child that does os.unshare(USER|PID|NS|NET|IPC), forks again to be PID 1 of the new pid ns, mounts /proc (and, variant b, bind-mounts a socket dir and a tmpfs scratch), and writes a byte to a pipe the jail program reads; 1 discarded + 20 runs, both users. Also the same with util-linux unshare --fork. Ratio = jail start median / bundle median.
3. Nesting (AC2): unshare --user --pid --mount --net --ipc --fork inside a strict_linux-style jail as root and tester; then each stopper: bwrap --disable-userns, --unshare-user --assert-userns-disabled, user.max_user_namespaces (lowered in a throwaway userns/host if writable), kernel.unprivileged_userns_clone and apparmor (read only if absent), seccomp (a filter blocking unshare/clone flags, if one can be loaded here).
4. PID 1 (AC3): bwrap --as-pid-1 --unshare-pid with a python3 PID 1 that also starts a sibling which sends SIGKILL / SIGSTOP to pid 1; then SIGKILL from the host to its host pid; observe via /proc/<pid>/status (State, SigBlk/SigIgn) and exit.
5. AC4: bwrap --help and a run for --ro-bind-data; cgroup mounts, a child cgroup under the v2 tree, cgroup.kill on a sleeping process.
6. AC5: tick or carry forward decision-0001's four open questions with dated lines.

## AC1a: a strict_linux() jail start (start_cost.py)

Per run: compile = `strict_linux().compile(spec, floors, ctx)`; launch = `SubprocessLauncher().launch(..., tether=fd)` returned; ready = `Handle.wait_ready("agent")` returned, i.e. a host connect() to the socket the jail's python3 bound and listened on succeeded. Then `Handle.kill()`, verified (every item ENDED). 1 discarded run, then 20. Milliseconds: median, IQR, range.

| | root | tester |
|---|---|---|
| compile | 0.5 (0.5-0.5; 0.4-0.6) | 0.5 (0.5-0.7; 0.4-0.8) |
| launch returned | 27.4 (26.4-30.7; 24.2-38.7) | 29.1 (27.1-33.3; 25.4-40.8) |
| **compile + launch to ready** | **127.6 (108.9-131.6; 106.4-151.9)** | **130.3 (128.7-134.8; 108.7-154.3)** |
| kill, verified | 11.2 (10.5-11.8; 9.9-38.0) | 11.4 (10.4-12.7; 10.1-14.3) |
| reference: brig's bwrap argv alone, python3 writes a byte to an inherited pipe | 17.9 (16.6-19.3; 16.1-21.4) | 17.8 (17.0-19.1; 16.1-22.3) |
| reference: brig's whole composed argv (trampoline, bwrap, sh/env -i), no exit wrapper, byte on a pipe | 75.1 (72.1-86.7; 66.2-96.8) | 83.2 (79.2-88.4; 74.3-101.0) |
| reference: python3 byte on a pipe, no jail | 12.9 (12.1-14.4; 11.5-18.7) | 13.7 (12.9-14.4; 12.2-16.0) |

Reading: bwrap itself costs about 5 ms over a bare python3 start. Most of a jail start is brig's own interpreters: the rlimits trampoline (the venv's 3.15 python importing brig.mech.trampoline) adds about 60 ms, the exit wrapper and launch bookkeeping about 25 ms, and wait_ready polls every 20 ms (readiness._POLL_INTERVAL_S), which is the two modes in the ready numbers (~108 and ~128). Root and tester are the same within noise.

## AC2: nested namespaces inside a strict_linux() jail (injail.py)

Inside the composed jail, `unshare --user --pid --mount --net --ipc --fork /bin/sh -c ...`:
- root: works (nested pid ns, the shell is pid 1). The jail runs in a user ns of its own (bwrap's --unshare-all tries one) as uid 0 with CapEff/CapBnd full and NoNewPrivs 1.
- tester: works (the jail has CapEff 0; the nested user ns is what makes the nested pid ns possible).
- `--mount-proc` (a /proc for the nested pid ns): tester works with no map, --map-current-user and --map-root-user. **root fails** (`mount /proc failed: EPERM`): run as root, bwrap covers /proc/irq and /proc/bus with read-only binds, so the jail's /proc is not fully visible and the kernel refuses a fresh proc mount in a less privileged user ns. As tester bwrap can't place those covers and /proc is bare. Root workaround observed: `umount /proc/irq /proc/bus` in the jail first, then the nested --mount-proc works. Root with `--cap-drop ALL`: the nested --map-current-user fails writing uid_map (mapping parent uid 0 needs CAP_SETFCAP); root with `--unshare-user --uid 1000`: mount-proc fails as above. So a supervisor's per-process /proc needs bwrap run as a non-root user, or a supervisor that removes the covers while it still holds the jail's capabilities.
- Without `--user`, `unshare --pid --mount --net --ipc --fork`: root works (it holds CAP_SYS_ADMIN in the jail's user ns), tester gets EPERM.

What stops it, tried here (both users unless said):
- `bwrap --unshare-user --disable-userns`: nested `unshare --user` fails ENOSPC. Root can still make pid/mount/net/ipc namespaces without a user ns (it keeps its capabilities); tester can't.
- `bwrap --unshare-user --assert-userns-disabled` alone: bwrap refuses to start ("creation of new user namespaces was not disabled as requested"), exit 1. With --disable-userns it starts and the nested user ns fails ENOSPC. `--disable-userns` without `--unshare-user` is refused by bwrap.
- `user.max_user_namespaces`: the host's is 64299 and not writable here (EACCES even as root), so it was lowered in a fresh user namespace around the whole run (lowered.py; the limit is per user ns and counts up the tree). Root: limit 2 nests, 1 refuses the nested one (ENOSPC), 0 refuses it too while bwrap still starts (as root --unshare-all falls back to no user ns). Tester: limit 2 refuses the nested one, 1 and 0 stop bwrap itself ("unshare user ns: ENOSPC"); bwrap 0.9 as tester used two user ns levels here, as root one.
- seccomp: a 13-instruction BPF program (nouserns_bpf.py: unshare/clone with CLONE_NEWUSER -> EPERM, clone3 -> ENOSYS) passed with `bwrap --seccomp 3`: nested `unshare --user` and `os.unshare(CLONE_NEWUSER)` fail EPERM for both; root still makes non-user namespaces, tester can't.

Only read about, not present here: `kernel.unprivileged_userns_clone` (Debian/older Ubuntu patch; no such sysctl on this kernel) and Ubuntu 24.04's `kernel.apparmor_restrict_unprivileged_userns` (absent; no AppArmor). Both act on unprivileged user ns creation, so they would stop tester's nested bundle (and bwrap itself, unless bwrap has an AppArmor profile or is setuid), not root's.

## AC1b: a namespace bundle start inside a running jail (bundle_cost.py, bundle_inner.py)

One strict_linux() jail (brig's composed argv, run directly) whose /usr/bin/python3 times each variant 1 discarded + 20 times. Ready = the new process wrote one byte to a pipe the jail's program reads. Variants: fork = fork(), child writes the byte; bundle = fork(), child `os.unshare(USER|PID|NS|NET|IPC)`, writes its own uid/gid map, forks again, the grandchild (asserted pid 1 of the new pid ns) makes / rprivate and mounts a fresh proc on /proc; bundle+mnt = also binds its own subdirectory over the channel directory and mounts a tmpfs scratch; bundle+py = bundle+mnt then exec /usr/bin/python3 that writes the byte; unshare(1) = util-linux `unshare --user --map-current-user --pid --mount --net --ipc --fork --mount-proc /bin/sh -c 'printf x >&FD'`. As root the program first detaches bwrap's /proc/irq and /proc/bus covers (AC2), which a supervisor would have to do too.

| ms: median (IQR; range), n=20 | root | tester |
|---|---|---|
| fork | 1.0 (0.9-1.1; 0.9-1.4) | 1.2 (1.1-1.4; 1.0-1.8) |
| bundle | 2.9 (2.8-3.0; 2.5-3.3) | 3.3 (3.1-3.7; 2.9-4.4) |
| bundle+mnt | 3.0 (2.8-3.2; 2.6-4.7) | 3.2 (3.1-3.4; 2.8-4.0) |
| bundle+py | 16.5 (15.8-18.8; 15.4-21.8) | 17.6 (15.9-19.1; 14.9-25.9) |
| unshare(1) | 3.1 (2.9-3.3; 2.7-5.0) | 3.2 (3.0-3.5; 2.7-4.4) |

**Ratio.** Jail start (compile + launch to ready) over bundle start: root 127.6 / 3.0 = 43x, tester 130.3 / 3.2 = 41x. With a python3 workload on both sides (jail start's ready is also a python3 that has bound a socket): 127.6 / 16.5 = 7.7x, 130.3 / 17.6 = 7.4x. The five namespaces and three mounts cost about 2 ms over a fork, and the mounts add nothing measurable. Against bwrap alone (17.9 ms, AC1a's bare reference), a bundle-plus-python start is about the same; the jail start's cost is brig's own interpreters around bwrap (trampoline, exit wrapper, readiness polling), not namespaces.

## AC3: what reaches a supervisor run --as-pid-1 (pid1.py)

brig's composed argv with `--as-pid-1` added (--unshare-all already unshares pid); bwrap execs /bin/sh which execs env -i which execs python3, so python3 is the jail's pid 1 (asserted), no handlers installed (SigIgn 0x1001000 = SIGPIPE and SIGXFSZ, SigCgt 0x2 = SIGINT, all CPython's own). A sibling in the jail sends signals to pid 1 and reads /proc/1/status 0.2 s later; then the host signals pid 1's host pid (found by NSpid) and reads /proc/<pid>/status. Same result as root and as tester:
- inside, SIGTERM, SIGKILL, SIGSTOP to pid 1: each kill() returns 0 and nothing happens: State stays `S (sleeping)`, pid 1 keeps running and prints after them (the kernel drops signals to a namespace's init that has no handler, SIGKILL and SIGSTOP included).
- host SIGSTOP: State `T (stopped)`; host SIGCONT: back to `S (sleeping)`. Tester did this to its own jail with no privileges.
- host SIGKILL: pid 1 is gone (no /proc entry), bwrap exits 137, and a /bin/sleep pid 1 had started in the jail is gone too (pgrep finds none): the pid namespace ended with its init.

## AC4: --ro-bind-data and cgroup.kill

- `--ro-bind-data FD DEST` is in bwrap 0.9's --help (with --bind-data and --perms). Run in brig's jail (`--perms 0444 --ro-bind-data 3 /sup/supervisor.py`, fd 3 a file the host opened): `python3 -I /sup/supervisor.py` runs it, as root and as tester; the file is mode 0444, owned by the jail's uid; appending to it fails (root: read-only file system; tester: permission denied). Available here.
- cgroup v2: this host is hybrid. v1 controllers are mounted at /sys/fs/cgroup/<controller>, and cgroup2 at /sys/fs/cgroup/unified with no controllers enabled; this process is in its root (0::/). No systemd, so nothing has delegated a subtree to any user. cgroup.kill exists in a child cgroup (it is a core file, no controller needed). cgkill.sh: as root, a child cgroup holding a shell, a sleep, a setsid() sleep and a SIGTERM-ignoring sh: writing 1 to cgroup.kill emptied it (5 procs -> 0, populated 0). Tester without delegation can't write a root-owned cgroup.procs (EACCES). With a subtree delegated by root (dir, cgroup.procs, cgroup.threads, cgroup.subtree_control chowned to tester), tester still can't move itself in from the root cgroup (the write fails: moving needs write access to the common ancestor's cgroup.procs), but once root placed tester's shell inside it (what systemd's user@.service delegation does), tester made a child cgroup, moved a group with a setsid() child into it and killed it with cgroup.kill (3 procs -> 0). So cgroup.kill works here, but the unprivileged fallback needs a subtree some privileged party (systemd, a container runtime) delegated and placed the embedder in; bwrap doesn't mount /sys, so the runtime on the host, not the supervisor, would write it.

## Where the numbers meet decision-0001's text (text left for the owner)

- "for a few system calls instead of a jail start" holds (about 40x). But a jail start costs ~128 ms mostly because of brig's own interpreters (the rlimits trampoline about 60 ms, the exit wrapper and launch about 25 ms, wait_ready's 20 ms polling); bwrap itself is about 5 ms over a python3 start.
- "with `/proc` mounted for its own pid namespace": true for an unprivileged embedder. As root, bwrap covers /proc/irq and /proc/bus, and the kernel then refuses a fresh proc mount in a nested user ns; the supervisor has to detach the covers first (observed to work) or run bwrap as a non-root uid. The decision doesn't say this.
- "the user namespace is what lets an unprivileged process create one": confirmed. As root the jail keeps full capabilities in its user ns (bwrap keeps them for uid 0 unless --cap-drop), so --disable-userns or a seccomp filter stops root's nested user ns but not its nested pid/mount/net/ipc namespaces. Side finding: strict_linux() run as root gives the workload CapEff/CapBnd full in its user ns.
- "the fallback is cgroup v2's `cgroup.kill` on a delegated subtree": it works here, but only in a subtree a privileged party delegated and placed the embedder in. An unprivileged embedder can't create that for itself, and bwrap jails don't see /sys, so the fallback belongs to the host-side runtime and needs systemd (or a container runtime) to have delegated it. On this host (no systemd) only root has it.
- "the kernel drops SIGKILL and SIGSTOP sent to it from inside, while a SIGKILL from the host still lands": confirmed, and a host SIGSTOP lands too.
- Migration step 0 names a jail-start measure on Linux and macOS: macOS is unmeasured (no Mac here).
