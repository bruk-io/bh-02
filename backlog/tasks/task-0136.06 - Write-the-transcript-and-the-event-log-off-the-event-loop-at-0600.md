## Implementation Plan

<!-- SECTION:PLAN:BEGIN -->
1. host_paths: new appender.py, Appender: one file, held fd (O_APPEND|O_CREAT|O_NOFOLLOW|O_CLOEXEC, 0600, optionally O_EXCL); append() sync queues a write on a one-thread executor (order = queue order, no running loop needed), flush()/close() async, shielded; a failed write is sticky: nothing after it is written and every append/flush/close raises it. Lazy open on the worker thread (FileTranscript) or eager Appender.open (EventLog). Own tests: order, link refused, mode, failure, cancel-safety. Gate budget + README/CLAUDE docs.

3. FileTranscript: append = queue the line then commit in memory; flush(); async context manager closes the appender (wiring enters it so a restart or a retired child releases the fd). rewrite creates new file + backup 0600. ## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
Changed: libs/host-paths/src/host_paths/appender.py (new Appender, exported), its tests test_host_paths_appender.py; subagents eventlog.py now writes through Appender.open(path, new=True) (tests untouched, 3 pass); agent transcript.py (FileTranscript.append queues, flush(), async context manager closes; rewrite makes .new and .bak at 0600 with O_NOFOLLOW and an fchmod for a stale .new), wiring.py (the row enters the file transcript so a restart or a retired child closes the fd), loop.py (reply = _reply inside aclosing + finally flush via a private optional _Flushable capability; the Transcript Protocol is unchanged, MemoryTranscript has no flush; CONTRACTS.md says so); bh_02 sessions.create mkdir(mode=0o700). Docs: CONTRACTS.md, agent and subagents READMEs, host-paths README/CLAUDE.md, CLAUDE.md files, GLOSSARY, docs/bh-02/how-it-works/loop.md. Purity budget: LoopModel._flushed added, eventlog._append removed, host_paths Appender.* added.

Design: one worker thread per Appender (ThreadPoolExecutor(max_workers=1)) gives the order and lets append() be synchronous with no running event loop (the old chained to_thread futures needed one); flush/close shield the wait so a cancelled waiter leaves the writes to finish. A failed write is sticky: nothing queued after it is written (no hole in a transcript), and every append/flush/close raises it (OSError with a note naming the file). The event log catches it and stops (best-effort kept). The file opens lazily on the first write (a read-only FileTranscript, /compact's, makes and holds nothing) or at once with Appender.open (EventLog, to keep its O_EXCL error at open).

Can a command run while a reply runs? No: chat.converse awaits the reply (_interruptible gathers the cancelled reply too) before it reads the next line, and jobs.settled() gates the restart a command queued; so the end-of-reply flush is enough and /clear and /compact never see a pending write.

Evidence (planted, each seen failing, then restored): appender without O_NOFOLLOW -> link test fails; mode 0o666 -> mode test fails; no skip of writes after a failure -> hole test fails (first version of that test did not catch it, tightened so only one write fails); unshielded flush -> cancelled-flush test fails (first version did not catch it either, now a write waits behind the held one); loop without the flush -> 5 loop tests and the /clear and /compact after-a-reply tests fail (they run with the row still open on a slow disk); rewrite with 0o666 / without fchmod / without O_NOFOLLOW -> the three rewrite tests fail; FileTranscript.append writing on the loop -> the held-write test hangs/fails; session mkdir without mode -> test sees 0o777 (511) not 0o700 under umask 0.
