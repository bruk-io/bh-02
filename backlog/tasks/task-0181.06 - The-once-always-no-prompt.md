## Implementation Plan

<!-- SECTION:PLAN:BEGIN -->
`output` gains `choose(question) -> str` beside `confirm`; `runner:grant_prompt` serves the broker (`Broker.serve`, its `Prompt`) through it; the words are one pure function in the runner plugin.

The question (CONTRACTS.md: question, a new `kind = "choice"`): `title`, `lines` (the four things of decision-0012 item 8, in order: what, who asks and why, when it applies, what it does to the grades), `warning` ('' for none), `choices` (each `{key, value, label}`, in order; the keys are single characters), `escape` (the value Escape answers), and `agent` when a sub-agent's. `choose` returns a choice's `value`, or '' when the question was withdrawn (Ctrl-C) or the app has ended.

The words (`runner_cordis_plugin/prompting.py`, pure, no cordis): `question(request, *, places, runtime_dir)` builds it from a `Request`:
- **What:** the kind and target (`read /x`, `write /x`, `env NAME`, `net example.com:443`).
- **Who and why:** the asker's source and name, then the reason in the asker's words.
- **When it applies:** what this build actually does, from one function so TASK-0181.07 and .08 change one place: a path or env grant applies from the program's next start (`/clear` starts the Python process again); a net grant from each program's next start, until .07 makes it live.
- **The grades:** `net` adds a destination, network stays proxied; `env` the variable's value reaches the program, no grade changes; `read` and `write` no grade changes, unless the path is, holds or lies under a socket place (brig's places the runner already refuses roots under, plus `XDG_RUNTIME_DIR`): then `warning` says network would be violated and approval would stop counting the jail as confined. A `write` on a self-modifying path (`SELF_MODIFYING` by name) warns that it can run code outside the jail later (item 10).
- **Choices:** `o` once (for this session), `a` always (for this project), `n` no; Escape answers `no`.

`runner:grant_prompt` (depends on `grants`, `output`, `asides`, `commands`) serves a prompt that asks `output.choose(question(...))` and maps the value to `Answer` ('' to None: withdrawn, nothing recorded, as the broker already handles). It adds an aside that tells the model, on the next call's result, each answer decided since the last call (granted once/always, or declined), and nothing for `standing`. Its `/grants` stays.

The TUI: a `ChoiceScreen` modal (widgets/, beside `ApprovalScreen`, the same `GRACE` and dimmed keys line, Ctrl-C withdraws) draws its keys from `choices`; `ports.py`'s output gets `choose` over the bridge as `confirm` does. Sub-agents: `Asker` and `Labelled` forward `choose` with the agent's label, as they do `confirm` (an unlabelled choice is withdrawn: ''). Every other `output` provider and fake (`bh_02.testing`, test fakes) gets `choose`.

The reviewer's finding on TASK-0181.05 goes here: `Broker.revoke` of a session answer that a held need still holds asks that need again (`_ask_held`) once a prompt is served, so its holder is not left silently without it.

### Order of work
1. `prompting.py` and its unit tests (each kind, the socket-place warning for read and write, under and holding, the self-modifying warning, an agent's label).
2. `choose` in the contract: tui `ChoiceScreen` and `ports.py`, sub-agents' `Asker`/`Labelled`, every fake.
3. `runner:grant_prompt` serving and the aside; the shipped layer row's new dependencies.
4. `revoke` re-asks held needs.
5. CONTRACTS.md (`output.choose`, the choice question), the runner and tui READMEs, GLOSSARY if a term is new.

### Risks
- `grant-prompt` now depends on `output` and `asides`: check it reloads with neither `approval` nor `runner` (the structural test from .05 extends to it) and that its reload releases the served prompt, so a question in flight is withdrawn as no, not left hanging.
- The modal's keys: TASK-0193 (keys judged when processed, not when typed) applies to `ChoiceScreen` as to `ApprovalScreen`; reuse the approval modal's arming, don't fork it, so the fix lands once.
- Two prompts at once (a need settled while an input's ask runs): the broker asks one at a time; the modal must not stack two.

### Proof
Unit tests for the words; Pilot tests that `o`, `a`, `n` and Escape answer their values only once armed and Ctrl-C answers ''; a wiring test, with a fake output, that each answer is kept as decided (once in the session, always in a temp store, no for the session) and a withdrawn one records nothing; a sub-agent test that its choice carries the label; `scripts/check` and `scripts/linux-jail-check` (both modes) exit 0.
