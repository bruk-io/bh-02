`llm.reply` yields text only, so the terminal can't show what the model did. A reply becomes a stream of events in the same vocabulary a completion already speaks, and the terminal renders them.

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
CONTRACTS.md: `event` = a chunk or thinking/tool_result/usage/stop; `reply` yields events, `output.show` takes them; consumers ignore types they don't know. chat modes pass events through unread. SDK: `events_of` replaces `text_of` (text/thinking from deltas only, tool_call from the finished AssistantMessage, tool_result from UserMessage, usage+stop from ResultMessage; input tokens include cache reads/creation). LoopModel yields every completion chunk plus a tool_result per call. terminal: pure `render.py` (ANSI, no new dependency) + `TerminalOutput` tracks which stream is mid-line; only text reaches stdout, so `bhh ask` stays pipeable (tested). A failed ask no longer prints an empty stdout line. usage/stop events from the loop come with 0009.05. Four stdio printing helpers added to the no-impure-functions budget with the existing terminal I/O entries.

AC #3 left open until 0009.05: the loop passes through a completion's usage/stop chunks, but ollama doesn't emit them yet.
