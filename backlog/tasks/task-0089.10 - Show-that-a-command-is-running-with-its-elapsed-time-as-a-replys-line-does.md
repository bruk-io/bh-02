## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Found while building TASK-0089.06. The working line (Working · 12s) follows the ui's TurnStarted/TurnEnded, which the output posts around output.show. A reply is shown as it streams, so it is covered; a command (a ! one, up to its 120 s timeout, /compact, /model) is shown only once it answers (chat.converse runs commands.run, then output.show(answer)), so while it runs the screen still shows nothing moving and the only word is Ctrl-C's 'a command is running'. The signal for 'a line is being handled' exists in the bridge (_busy: a line handed out, nobody has read since) but not as a public one the app can follow, and it is true of a reply's start too. Decide in the plan where the app learns a command began and ended (the bridge already hears read() and line handed out), and whether the line says the same thing for a command.
<!-- SECTION:DESCRIPTION:END -->

## Implementation Plan

<!-- SECTION:PLAN:BEGIN -->
Decision: the bridge tells the app. Where the app learns a command began and ended: the Bridge (ports.py) already hears the line handed out (submit, or a kept line taken by read) and the next read(); it gets a public `handling` (a line handed out and nobody has read since, and its answer has not said it restarts rows) and posts a `Handling(busy)` message at every flip, as the output posts TurnStarted. The app (BhApp.on_handling) keeps the flag and times the Working line while a reply streams OR a line is being handled. Nothing else is told: the chat row, CONTRACTS.md and the `input`/`output` shapes do not change, and tui:ui still depends on its config alone.
- Why not the output: show() is called by a reply, by a command's answer and by a command's own notes (/compact says it is asking the model, runs a minute, then answers), so a show cannot tell them apart; the bridge hears the line, not what is shown for it.
- Why not only `_busy` to the next read: a /clear, /model or /compact answer then waits for its queued restart (jobs.settled) with the line still counting, but the criterion says it goes when the command answers. The answer's `restarting` event is already handed to the bridge (announce), so `handling` is also false from then on.
- Messages carry the value (not a bare "changed"): a kept line is taken right after a reply's read, and False then True must restart the count from zero, as the next reply's does today.
- Same line for a command (Working · 12s): the criterion says the same timer line; "Working" is true of a command that runs. A reply keeps its own start (TurnStarted/TurnEnded stay, so a reply without a bridge line, as the existing tests drive it, is unchanged), the line is shown while either holds, and begin()/end() are idempotent, so the first of the two starts it and the last to end stops it. Hidden until the first tick, so a quick command's answer never flashes it.

Order of work:
1. messages.py `Handling`; ports.py Bridge(post=None), `handling`, `_tell` called where `_busy` or `_announced` or `_ended` change (submit, line, announce, end); BhApp builds Bridge(self.post_message).
2. app.py: `_handling`, `on_handling`, `_follow_working` used by on_turn_started/on_turn_ended/on_handling.
3. Tests (tests/test_tui_command_working.py, new; Pilot with the real Bridge, TuiInput, TuiOutput and a reader standing for the chat row; bridge-level posts without Pilot): a ! command running shows the line and counts, goes at its answer; /compact-like (own note through show, then runs on) keeps it through the note and ends at the answer; a quick command never shows it (content empty); an answer that restarts rows ends it while no read has come; a kept line after a reply restarts the count from zero; Esc says and does nothing, Ctrl-C is held and the `a command is running` note comes as before, with the line up; a reply's line as before with a line handed out; the app leaving (Ctrl-Q) while a command runs ends cleanly. Each seen failing with the code removed.
4. README Working paragraph and bridge paragraph, docs commands.md line about commands, app docstring.
5. scripts/check bh-02/plugins/tui-cordis-plugin at the end (and bh-02/app --no-gates --no-docs only if the app is touched: it is not).
Risks: a flag stuck True after a read that never comes (the line would count forever): handling is false once ended and at every read; a restart mid-command (chat row cancelled): the new row's first read clears it; the line during a question's modal is unchanged.
