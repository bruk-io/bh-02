## Implementation Plan

<!-- SECTION:PLAN:BEGIN -->
The requesters of decision-0012 items 4 and 5: an input asks with `grant(...)`, a path or env grant restarts the program it is for before its next input, a plugin's standing need is asked before the first start, and an extension's request is asked like any other.

**`grant` is a tool.** `runner:grant_prompt` registers a `grant` tool in `tools` (decision-0012 item 1's kinds: `kind`, `target`, `port` for net, `reason`), so an input calls `tools.grant(kind=..., target=..., reason=...)` across the socket the way every tool is called (the worker's `op: call`), and the model may call it directly too. Its run is `grants.ask(Request(..., Asker(Source.INPUT, "python"), reason))`, and its result says the outcome in words the model can act on: for a path or env grant, that it holds from the next input, after the Python process starts again and loses its variables; for net, that it holds now. A bad request (`Invalid`, on the floor) is a result that says why, not an exception. The tool tells the model of itself in a `system` section (the loop knows no tool by name), never in its spec's description. The tool is `runs="harness"` (bh-02's own tool, bounded to bh-02's own state: the broker), which `approval` already lets through unasked when the runner confines, so the person is asked once, by the broker's question, and the approval rule gains no case. Under `--no-jail` there is nothing to grant (no jail): the tool says so and asks nothing.

**Restarts.** The broker gains `generation() -> int`, which changes whenever the session's read, write or env grants change (an answer, a revoke, a need held or released; not a net grant, which is live). The python client records it at each worker start and, before an input, when it differs, starts the worker again first and opens the input's result with why (the prefix it already writes after a restart), so the model is told; the person sees the same line. The python row takes `grants` as a dependency through a Protocol of its own (`generation`), which costs no reload (the grants row depends on `host` alone). The extensions host does the same, at once on a change rather than before an input (item 4). A revoke of a path or env grant takes effect the same way, so a revoked read grant stops at the next input.

**Standing needs.** The python row's config gains `needs` (a list of `{kind, target, port, reason}`), each held with `grants.need` while the row is up (acquired, leaving with the row). Before its first worker start the client awaits `grants.ready()`, a broker method that returns once every held need has an answer, or at once when no prompt is served; a need costs no restart, because it is answered before the process exists. A layer-written runner `config` (`write`, `env`) stays unasked (item 5).

**Extensions.** The extensions host offers its extensions `grant(...)` in their API (four keys that only add: through `grants`, never `runner`), asked as `Source.EXTENSION` with the extension's name.

**Sub-agents.** A child's python row names its asker as the agent (`Source.AGENT`, the agent's label), and its program's refusals name the agent too (`owner`), so the person sees which agent asks (the label .07 left to this task).

### Order of work
1. `Broker.generation` and `Broker.ready`, with unit tests.
2. The `grant` tool (`runs="harness"`) and its `system` section.
3. The python client's restart before an input, and `needs`; the extensions host's restart and `grant`.
4. Sub-agents' label.
5. CONTRACTS.md (`grants`, `tools`' `grant`, `python` config), READMEs, GLOSSARY.

### Risks
- The python row's new `grants` dependency must not reload it (a reload loses the namespace): the structural test from .05 extends to `python` and `extensions`.
- A restart that loses an input's variables mid-reply: only before an input, never during one; a test runs an input that grants and checks the variable survives to the end of that input and is gone after.
- `ready()` waiting forever: no prompt served answers at once; a withdrawn question counts as answered (no).
- `grant` unasked by approval must not become a way to run anything else: its only effect is a question to the person, and a request the floor refuses is refused before anyone is asked.

### Proof
A real-jail test: an input calls `tools.grant(kind="read", target=DIR, reason=...)`, a fake prompt answers once, the next input reads DIR after a restart whose words reach the model, and a variable set before is gone. A wiring test: a python row's `needs` is asked before the first worker start and no restart follows. A test that an extension's `grant` is asked as an extension. A sub-agent test that its request is labelled. `scripts/check` and `scripts/linux-jail-check` (both modes) exit 0.
