### What a workload could do to the supervisor, and why it can't
- Signal it: the kernel drops SIGKILL and SIGSTOP from inside a pid namespace to its init, and every signal the init has no handler for (observed, above). The host's SIGKILL does land and ends the namespace, a `setsid()` child included.
- Read or change it: `prctl(PR_SET_DUMPABLE, 0)` makes `/proc/1/{environ,mem,maps,fd}` unreadable, and ptrace attach and `pidfd_getfd` fail without CAP_SYS_PTRACE; the jail drops every capability (`--cap-drop ALL`). Probed by `test_a_process_of_the_jail_can_not_read_attach_to_or_take_from_the_supervisor`.
- Reach the socket: it is passed to nothing the supervisor starts (every child closes everything above its three stdio fds before exec); the check lists every process's fds.
- Replace its code or interpreter: `--ro-bind-data` source in a read-only root, run with `-I` and an empty environment (no PYTHON* variables, no cwd or user site on the path); the interpreter lives on a read-only mount.
- Make it import something hostile later: every import is done before the ready message, then `NoMoreImports` refuses any (planted lazy import seen failing the request, below).
- Starve it: the supervisor's CPU time is bounded only by the inherited per-process RLIMIT_CPU, not the sum over the jail. Not closed here; `control` and `channel_exclusivity` stay `unenforced` until TASK-0079.08's battery says what the report names.
- Escape its group kill: `stop` is group-shaped, so a `setsid()` child escapes `stop` (not destroy) until TASK-0079.07's per-process namespaces.

## Reopened by the closing review (2026-10-15): the tripwire ended the jail about 2 s late

**Correction.** The sentence above that said `destroy` "closes the socket, then kills" had the order reversed. A plain `destroy()` ladders each process first (SIGTERM, up to 2.0 s, SIGKILL), then closes the link and ladders the instance. With the tripwire armed as `wire.arm(running.destroy)` a program that ignored SIGTERM and rewrote the absent secret every 10 ms planted it on the host 3 runs in 3, the jail ending after 2.01 to 2.06 s (the reviewer's probe); the `killpg(SIGKILL)` it replaced ended the jail in about 0.01 s.

**Fix, SPEC first: decision-193 (2026-10-15).**
- brig: `Jail.destroy(*, grace=2.0)` and `Runtime.destroy(jail, *, grace)`. `grace=0` is `SIGKILL` at once with no `SIGTERM`. In a supervised jail the instance's group is signalled first, its leader's identity read from `/proc` and no `ps` before the signal, so the kernel ends every process in the namespace, a `setsid()` child included; then each item is verified in the report's usual order, a process that ran before the signal reported `ENDED` and not `ALREADY_GONE`. A missed request deadline and a supervisor that never said it was ready end the instance with `grace=0` too. `Jail.instance_group` names the group that holds the PID 1 (None where there is no supervisor).
- runner: the tripwire is armed with `still_running(running.destroy(grace=0.0))`; when brig's teardown raises it falls back to a `SIGKILL` of the jail's group and says so, and a teardown that reports a `FAILED` item says what may still run, both in `tripped`, which is the answer the person reads (`unended_for`). The record's group is now `Jail.instance_group`, not the program's pid, so a jail a `setsid()` server keeps alive after its program ended reads live to the sweep. `_recorded_group` / `_gone` in the runner tests now verify the jail: `_jail_group` asserts the recorded group holds a PID 1.

## Two failures of the full check under load (2026-10-15), each with its cause

**1. `test_a_start_on_a_jail_whose_tether_has_ended_is_refused_before_anything_is_made` (mine): the tether had not ended yet.** The check is synchronous (`HeldTether.fd` polls the read end with no wait). The hangup it reads is not: a pipe's read end hangs up when *every* write end is closed, and a child that another thread of the test process forked, and that has not yet exec'd, holds a copy of every descriptor until it does. The suite's own leak poller forks `ps` every 50 ms from its thread. Under four CPU-bound processes (`loop_under_load.sh`, scratchpad) I saw the child directly: in 2 closes of 60 the test closed its write end, the read end showed no hangup, and a child of the test process (still carrying the test's command line, so not yet exec'd) held the pipe on fds 7, 8 and 9; the hangup arrived 1.5 and 2.4 ms later. A start in that window is not refused, which is correct: the tether had not ended, so the process is started and its watcher (here the supervised jail's own) ends it when the copy goes. That showed as `DID NOT RAISE TetherClosed` (the start returned) and, in the other run, as `SupervisorGone: the supervisor's socket closed while 'go' was waiting` (the tether killed the instance mid-start). Reproduced before the fix: 2 failures in 60 runs. Decision: the code needs no change, and says so (SPEC.md section 8, TASK-0079.25 point 2, and `HeldTether.fd`: the check promises the pipe's state at that moment, and a tether has ended when every write end is closed). The test now waits, bounded, for the hangup on its own `dup` of the read end (`tether_has_ended` in `tests/conftest.py`) before asserting the refusal, and a new test shows the other half with a deterministic stand-in for the forked child: `test_a_tether_has_not_ended_while_any_copy_of_its_write_end_is_open` (a copy held open: the start is not refused and its watcher ends it when the copy is closed; the control: with the copy closed the same start is refused). After: 0 failures in 140 runs of the same loop.
The sibling `test_a_start_on_a_tether_that_has_ended_is_refused_and_makes_nothing` (test_host_records.py, not in the failing list) failed 5 times in 40 under the same load for a related reason found on the way: it ended with the control's group still being ended by its watcher (the tether having just ended), and the suite's leak sweep read the group at teardown (`pgid=alive`). It now waits for the group to be gone, a claim it was making implicitly. After: 0 in 40.

**2. `bh-02/plugins/commands-cordis-plugin/tests/test_shell_command.py::test_a_program_left_holding_the_output_ends_with_the_command_one_that_let_go_does_not` (a pre-existing test of the commands plugin, not mine): the program was killed and had not finished dying.** `run_command` ends a program left holding the output with `killpg(SIGTERM)` then, as the shell has already exited, at once `killpg(SIGKILL)`, and returns when the output it reads reaches end-of-file. The kernel closes the dying program's descriptors in `do_exit`, before it is a zombie, so end-of-file arrives while the process is still `R`. Measured under the same load with a loop that read `/proc/<pid>/stat` right after `run_command` returned: 1 of 150 returns found the program in state `R`, and it was `Z` 0.39 ms later. So it is not a program that survives, and `run_command` cannot wait for the kernel's exit without a wait of its own for no one's use; the test's `_alive(pid)` asked at the one moment the answer is not yet settled.
