## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Owner's pick (2026-10-15): nothing in the TUI copies; Textual's own selection copy loses to the app's priority Ctrl-C. Chosen by the orchestrator, for the owner to overrule: Ctrl-C copies when text is selected and stops a reply otherwise, and one more key copies the newest reply whole. ## Implementation Plan

1. Build on Textual: every copy (screen.copy_text for Ctrl-C/super+c, TextArea copy, ours) ends in App.copy_to_clipboard, so BhApp overrides it to say how much in one line (a toast, not a transcript note: a note would split a streaming reply).
2. app.py: action_interrupt = _copy_selection() or _stop(): copy the composer's own selection when focused, else the screen's, clear it so a second Ctrl-C stops, never while a question is up. ## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
Finish moved before work began: the owner's users are on macOS in Ghostty, kitty or WezTerm, where Cmd-C can reach bh-02 as super+c (kitty keyboard protocol), and they asked for copy on select as well

Built on Textual's own copy rather than around it: Screen binds "ctrl+c,super+c" to screen.copy_text and TextArea binds the same keys to its copy, all of which end in App.copy_to_clipboard (an OSC 52 write plus Textual's record in app.clipboard). BhApp overrides copy_to_clipboard to also say how much in one line ("Copied 120 characters", render.copied_line), so every way of copying says it alike. The line is a toast (App.notify, markup=False, 3 s), not a transcript note: Transcript.note closes the open stream, so a note drawn while a reply streams would split the reply mid-paragraph (the app already holds the person's typed lines until the reply ends for this reason); a test copies during a streaming reply and sees one text block.
Ctrl-C (AC1): action_interrupt = _copy_selection() or _stop() (the old body). It copies the composer's own selection when the composer has the focus and some, else the screen's (get_selected_text, the transcript's), clears it (composer: cursor alone; screen: clear_selection) so a second Ctrl-C stops the reply, and never copies while a question is up (Ctrl-C then answers it no, as before; a selection in the modal itself is ignored). I included the composer's selection: with a priority Ctrl-C it would otherwise stop the reply under someone who meant to copy. Esc never copies (_stop directly; Esc also clears a selection first, Textual's own Screen._key_escape, so that plant cannot be told apart).
Cmd-C (AC5): nothing to build; super+c is Textual's binding and the app's priority binding is ctrl+c only. The test presses super+c with the focus in the composer (its copy has nothing selected and passes) and in the transcript (where a mouse selection leaves it), reply running: copied, reply not stopped. Planted a priority super+c -> bell binding: both cases failed (a first plant routing super+c to action_interrupt passed vacuously, since that copies too, and was replaced).
Copy on select (AC6): BhApp.on_text_selected (the screen posts TextSelected at every mouse up, a click included) copies get_selected_text() when it is 2 or more characters; a click or one character copies nothing and says nothing; the selection stays shown. Transcript selections only (a composer drag is the text area's own and TextSelected finds nothing screen-side).
The key (AC2): Ctrl-T copies the newest reply whole. Why: it is bound by no composer, screen or app key (a test walks the BINDINGS of Composer's MRO, Screen, App and BhApp and the palette's key), terminals keep none in raw mode, and the nearer candidates are taken in meaning: Ctrl-O is Claude Code's and what TASK-0089.07 (expand a clipped result) will want, Ctrl-R and Ctrl-N are readline history, Ctrl-G opens an editor, Ctrl-Y is the composer's redo, Ctrl-L is clear. It is a plain non-priority binding, so a question up (modal) cuts it off. "Reply" is the glossary's turn: render.newest_reply takes every text block after the last user block in order, joined by a blank line, as the model wrote them (Stream.text, the markdown source, not what is drawn); thinking, tool calls and usage are left out; while the newest message has no text yet it is the reply before. The owner may prefer the last text block only: it is the one line to change in newest_reply. With none: "Nothing to copy: no reply yet".
