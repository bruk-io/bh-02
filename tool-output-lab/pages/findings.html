Summarising large tool outputs for Claude Code

When a tool returns a large output, such as a long log or a big JSON response, Claude Code either puts all of it into the model's context or, if it is larger than Claude Code's limit, saves it to a file and shows the model a short preview. We tested a third option. A Claude Code hook, a script that runs after every tool call, replaces each large output with a short summary, which we call an envelope, and saves the full output to a file that the model can still open. We wanted to know whether the model still answers correctly with the envelope, and how much context it saves.

Results

The model answered at least as well with the envelope as without it in every test, and it used less context each time.

We tested on 104 tasks that we built. Each task is a tool output with a question about it, and we planted the answer in the output, so we know what the right answer is. The outputs are lists of Kubernetes pods in JSON, web server logs, accessibility snapshots of web pages, and Figma design files. Each comes in a medium size, which fits within Claude Code's limit, and a large size, which does not. Forty of the tasks ask the model to find a problem in the output, which is where a summary is most likely to hide something.

Each task ran twice in Claude Code, once with the hook and once without it, and we compared the two runs task by task. We ran the final version of the envelope three times.

Context here is the number of tokens the model read on its last request. Each run also cost 25 to 29% less, as charged by the API.

Before the runs, we decided that the envelope would pass if correct answers fell by no more than 3 percentage points and the context got smaller. Haiku passed on both counts. Sonnet used less context and answered all 40 tasks correctly, but 40 runs are too few to rule out a drop of more than 3 points. With an earlier version of the envelope, Sonnet answered 103 of the 104 tasks correctly, against 104 without the envelope.

On the 40 find-the-problem tasks, Haiku did 10 points better with the envelope than without it, which is more than chance would explain (the 95% range is 3 to 19 points). Without the envelope, Haiku missed problems in the large snapshots and Figma files, where it only gets a preview and has to search the saved file.

How much the envelope saves depends on the size of the output. Without the envelope, the model holds a medium output in full, so replacing it saves more. A large output is already replaced by a preview, and the model searches the file for what it needs. These are Haiku's 104 tasks split by size.

Medium runs cost 18% less but took about 3 seconds longer, because the model often opened the full output after reading the envelope. Large runs cost 31% less and were about 9 seconds faster.

How the envelope works

When a tool's output is larger than 2,000 tokens, the hook saves the output to a file and gives the model an envelope in its place. The envelope has four sections, each labelled in the text:

  • shape: describes the output and gives exact counts, worked out over the whole output.
  • anomalies: lists the items that differ from the rest, with the position of each in the output.
  • samples: copies a few items exactly, chosen because they contain words from the tool call.
  • get more: gives line numbers and ready-made commands for reading the rest of the saved file.

A banner above the four sections says where the full output is saved. It also tells the model that every count is exact and that it should open the file only for what the envelope does not show.

The hook builds envelopes with the same four sections for logs, page snapshots, XML, web pages, plain text and source code.

How the envelope fits its budget

Each section can be written at a few levels of detail. The hook starts every section at its shortest, then adds detail in order of importance (shape, then anomalies, then get more, then samples) for as long as the envelope stays under 2,000 tokens. Most envelopes come out much smaller than that, and for our test outputs they were a few hundred tokens.

How we check the envelope

Before a model sees any envelope, a separate program checks it against the full output. We wrote this program apart from the code that builds envelopes, so that a mistake in one is unlikely to be repeated in the other. It counts every number again, compares every copied line with the original, and runs every command the envelope suggests to see that it prints what the envelope says. We tested 251 outputs, which include real logs, source files and recorded tool results as well as our test outputs, and the program found no mistake in any of their envelopes.

Heuristics

The hook decides everything in an envelope with fixed rules, and no model is involved. We set the thresholds by hand and checked them on our test outputs, but we have not tuned them systematically.

Every output

  • When to build an envelope. When the output is over 2,000 tokens, and only if the envelope is at most 90% of the output's size.
  • Measurements. Numbers of six or more digits, such as sizes and timestamps, are never treated as categories or as outliers.
  • Unusual numbers. A number more than three interquartile ranges outside the middle half.
  • Error words. A fixed list that includes error, failed, fatal, exception, traceback, panic, crash, timeout, denied and invalid.
  • Copied items. Items that contain a word from the tool call, skipping words that more than 5% of the lines, or 20% of JSON rows, contain.

Logs and other line-by-line output

  • Patterns. Two lines follow the same pattern when they match after every word that contains a digit, or an id of six or more hex characters, is replaced by <*>.
  • Unusual lines. A pattern on 1% of the lines or fewer, or a pattern with an error word on 10% of the lines or fewer.
  • Unusual values. In a <*> that holds six values or fewer, where one value is on 80% or more of the pattern's lines, a value on 2% of its lines or fewer.
  • Zeros. A zero or a negative where every other value is 10 or more.
  • Long lines. Cut at 300 characters, and the envelope says how many characters it cut.

JSON

  • Unusual rows. When 75% or more of the rows share a value, the rows whose own value is on 10% of the rows or fewer.
  • Unusual keys. Rows that have a key only 10% of rows have, or lack a key 90% have.
  • Unusual types. A value of another type than the rest of its field.
  • How many are listed. Up to 25 unusual rows per list, and fewer when the budget is tight. The envelope gives the total and says how many it lists.
  • Long values. Cut at 60 characters.

Page snapshots and other outlines

  • Groups. A node with five or more children, 60% or more of whose first lines follow one pattern, is a group of similar items. Quoted text also counts as <*>.
  • Unusual items. Items that hold a line or a value found in 20% of the items or fewer.
  • Error lines. A line with an error word, when 10% of the items or fewer have one.
  • Zeros. A zero or a negative where every other value is 10 or more.

Because the rules are fixed, the envelope finds the kinds of problem they describe and can miss others. The checking program shows that what an envelope says is true, but it cannot show that the envelope found everything. We planted the problems in our test outputs ourselves, knowing the rules, so the test tasks are likely kinder to the envelope than real outputs are.

The $0.00 invoice described below was a problem that no rule covered until we added the rule for zeros, and on a real Hadoop server log, whose problems were labelled by the people who published it, only 10 of 20 questions could be answered from the envelope alone. This is why, when the envelope finds nothing unusual, it lists the checks it ran and says that they do not prove there is no problem.

Other measurements

Changing one section at a time

We changed one section of the envelope at a time and counted how many questions could still be answered from the envelope alone. The anomalies: section made the biggest difference.

A missed answer and what we changed

In one task, an accessibility snapshot listed invoices, and one of them had an amount of $0.00. In an early run, the envelope's anomalies: section said "none", and Sonnet answered that nothing was wrong, even though it opened the file. We made two changes. The envelope now flags a number far from the rest, such as a zero among amounts between 20 and 900, and when it finds nothing, it lists the checks it ran. The task came in both sizes, so there were two such tasks.

Before the changes, Haiku found the invoice by searching the saved file. After the changes, neither model reported a problem in any of the 24 runs where the output had none.

How often the model opens the full output

With the envelope, the model does not need the saved file to answer these questions, but it often opens it anyway. Without the envelope, it opens the file for each of the 52 large outputs, because it only has a preview. Adding a sentence to the banner that says every count is exact made Haiku open the file less often, and it lost no answers.

Opening the file less often hardly changed Haiku's context, because most of these reads are small searches that add about 1,000 tokens.

When the model opened the file, it mostly ran its own searches to check what the envelope had said. For example, after the envelope had counted the hidden cards in a Figma file, the model counted them again with grep. It used line numbers from the envelope in 12 to 27% of its reads, and it seldom ran the commands in get more:.

Other versions of the envelope

We compared the final version's base with four other versions on Haiku, and none did clearly better.

Show the five versions and how each did

All five versions are built by the same code. The base version is the final version before the two changes for the $0.00 invoice and the banner sentence. The others change it in one way each:

  • The version with an example item also copies one ordinary item.
  • The shorter version has a shorter shape: section and copies no items.
  • The version with a command per group also gives a ready-made command for every group of similar items.

In an earlier run, we also tried a fifth version, which copies the first and last items of the output where the base version copies the items the tool call names. In that run, it answered all 104 tasks correctly and saved 7,390 tokens per run, against 6,688 for the base version, but it opened the file in 87 runs against 72. The shorter version made Haiku open the file more often, so it saved less than the base version. The differences were small, so we kept the base version.

What is not settled

  • Sonnet ran the final version on only 40 tasks, which is too few to rule out a drop in correct answers of more than 3 points.
  • Without the envelope, Claude Code answers 96 to 99% of our test tasks correctly, so these tasks show a loss more easily than a gain.
  • We ran Haiku on 59 real tasks from MCP-Atlas, a benchmark of tasks that use MCP tools, by replaying the tool outputs recorded in it. In about half the runs, the model's tool call differed from the recorded one and the replay returned a smaller output, so the hook had nothing to replace. The table below counts only the runs where the hook did replace an output with the base version. In those runs, the context was 3,788 tokens smaller and the cost 3% lower.
  • For JSON, the envelope does not yet flag a zero among numbers that are all 10 or more, as it does for logs and page snapshots.
  • We have not yet tested long sessions, where the model asks several questions about one output.

How we tested

Headless Claude Code with Haiku and Sonnet, about $43 of model runs in all

The model runs used headless Claude Code (claude -p) with Haiku and with Sonnet, and cost about $43 in all. Token counts and costs come from the API's own figures. The 95% ranges for correct answers use Newcombe's method for paired results, and those for tokens and cost use the bootstrap. The checking program runs without a model, so it costs nothing, and it ran on every version of the envelope before any model saw it. The example envelopes on this page were made by the hook's own code.
